# Как устроен семинар в этом репозитории

Документ описывает соглашения, по которым собраны семинары 1 и 2. Держитесь
их при добавлении следующих — тогда студенту не придётся заново разбираться,
что где лежит.

## Именование

| Что | Правило | Пример |
|---|---|---|
| Папка семинара | `seminar-NN-тема`, номер с ведущим нулём, тема латиницей | `seminar-03-slices` |
| Папка примера | `NN-тема` внутри `examples/` | `examples/02-strings-runes` |
| Папка задачи | `taskNN-тема` внутри `tasks/` | `tasks/task01-divmod` |
| Пакет задачи | короткое имя по теме, без номера | `package divmod` |

Ничего дополнительно регистрировать не нужно: `Makefile` находит семинары
по маске `seminar-*`, так что `make test`, `make check` и `make test-03`
заработают сразу. Руками правится только таблица семинаров в корневом
`README.md`.

## Структура папки

```
seminar-NN-тема/
├── README.md                конспект семинара (необязательно)
├── examples/                (необязательно)
│   └── NN-тема/main.go      запускается go run, живёт в package main
└── tasks/
    ├── README.md            карта задач
    └── taskNN-тема/
        ├── solution.go      заготовки: сигнатура + doc-комментарий + panic
        ├── types.go         типы и sentinel-ошибки (необязательно)
        └── solution_test.go тесты, они же условие задачи
```

Обязателен только `tasks/`. У семинара 3 нет ни конспекта, ни примеров —
`Makefile` подхватывает каталоги по факту их наличия, править его не нужно.

Конспект допустимо назвать иначе, если так понятнее: у семинара 2 он
называется `theory.md`, потому что почти всё занятие уходит на задачи,
а текст читается дома. Ссылку из корневого `README.md` тогда правят руками.

`types.go` появляется, когда у задачи есть собственные типы или
sentinel-ошибки. Его студент не правит — это фиксирует API, на который
рассчитан тест. Начинайте файл комментарием, что менять его не нужно.

## Скелет конспекта

Порядок разделов в конспекте семинара:

```markdown
# Семинар N. Тема

## Что будет к концу пары      ← список умений, а не тем
## План (тайминг для преподавателя)
## 1. Первый блок (00:00–00:15)
...
## N. Задачи (01:20–01:30)
## Чего мы сегодня НЕ трогали   ← чтобы снять вопрос «а почему без X»
## Материалы семинара           ← таблица: файл примера → о чём он
```

Тайминг проставляйте в заголовках разделов — на паре видно, укладываетесь ли.

## Соглашения по задачам

`solution.go` — только заготовки, реализации в репозитории нет:

```go
package divmod

// DivMod возвращает частное и остаток от деления dividend на divisor.
//
// При divisor != 0 результат совпадает с dividend / divisor и dividend % divisor.
// При divisor == 0 возвращает нулевые частное и остаток и ErrDivisionByZero.
//
// Паниковать при ожидаемой ошибке нельзя.
func DivMod(dividend, divisor int) (quotient, remainder int, err error) {
	panic("TODO: реализуйте DivMod")
}
```

Правила, которые делают задачи одинаковыми на ощупь:

1. **Тело заготовки — `panic("TODO: реализуйте ИмяФункции")`.** Не `return ""`:
   пустая заглушка иногда случайно проходит тест и создаёт ложное ощущение,
   что задача решена.
2. **Doc-комментарий — это условие, и только контракт.** Что принимает, что
   возвращает, как ведёт себя на границах. **Никаких подсказок о способе
   решения:** ни «используйте …», ни названий функций и пакетов стандартной
   библиотеки, ни разбора по шагам. Проверяйте каждое предложение вопросом
   «это про ЧТО или про КАК?» — про «как» вырезайте. Разбор подходов, типичные
   ошибки и наводящие вопросы живут в `solutions/<семинар>/notes.md`, который
   не публикуется. То же правило действует для `tasks/README.md`: студент
   видит его, значит подсказок там тоже нет.
3. **Тесты открытые и табличные**, имена подтестов по-русски — по выводу
   `go test -v` сразу видно, какой случай упал:

   ```go
   {name: "остаток", dividend: 17, divisor: 5, quotient: 3, remainder: 2},
   ```

4. **Сообщение об ошибке показывает вход, результат и ожидание:**

   ```go
   t.Errorf("Has(%03b, %03b) = %t, ожидалось %t", current, required, got, want)
   ```

5. **Где возможно — тест на свойство.** Он ловит случаи, которые не попали
   в таблицу: независимость двух счётчиков, отсутствие общих узлов у исходного
   и скопированного дерева, неизменность входных данных.
6. **Граничные случаи закладывайте в условие явно:** пустая строка, `nil`-слайс,
   ноль, отрицательное число. Иначе они всплывут на паре как спор.

## Чеклист нового семинара

- [ ] Папка `seminar-NN-тема` с `README.md`, `examples/`, `tasks/`
- [ ] Конспект: тайминг в заголовках, раздел «Материалы семинара» заполнен
- [ ] Каждый пример запускается: `go run ./seminar-NN-тема/examples/...`
- [ ] У каждой задачи есть `solution.go` с `panic` и `solution_test.go`,
      а если нужны свои типы — ещё и `types.go` с пометкой «не править»
- [ ] `tasks/README.md`: таблица задач и разбор условий
- [ ] Задача решается по условию — вы прошли тесты своим решением
- [ ] `make check` зелёный
- [ ] `make test-NN` падает ровно на `panic: TODO` и ни на чём другом
- [ ] Строка про семинар добавлена в таблицу корневого `README.md`
