## 1. Методы (00:00–00:15)
[`examples/01-methods`](examples/01-methods/main.go)

Метод — это функция с **получателем** (receiver), привязанная к типу:

```go
type Counter struct {
	n int
}

func (c Counter) Value() int { return c.n }  // получатель по значению
func (c *Counter) Inc()      { c.n++ }        // получатель по указателю
```

Методы можно объявлять только на типах из **своего пакета** — приклеить
метод к `int` или `string` из чужого пакета нельзя. Нужен метод на числе —
объявите свой тип: `type Percent int`.

**Значение или указатель?** Правило выбора короткое:

- метод **меняет** состояние → только указатель, иначе изменения умрут
  в копии;
- тип **большой** → указатель, чтобы не копировать структуру на каждый вызов;
- тип маленький и **неизменяемый** (как `time.Time` или `Money` из задачи 1)
  → значение, так безопаснее: метод физически не может ничего испортить;
- **не смешивайте** оба вида на одном типе — выбирайте один стиль.

Компилятор сам подставляет адрес и разыменование там, где это однозначно:

```go
c := Counter{}
c.Inc()      // на самом деле (&c).Inc()
p := &c
p.Value()    // на самом деле (*p).Value()
```

Но магия работает только для **адресуемых** значений: `Counter{}.Inc()`
не скомпилируется — у временного литерала нет адреса.

> **Углублённо: наборы методов (method sets).** У типа `T` набор методов —
> это методы с получателем `T`. У типа `*T` — методы с получателем `T`
> **и** `*T`. Поэтому значение `Counter` удовлетворяет интерфейсу
> `interface{ Value() int }`, а интерфейсу `interface{ Inc() }` — нет:
> `Inc()` требует указателя. Это правило станет критичным через раздел,
> когда интерфейсы перестанут компилироваться «сами собой».

## 2. Интерфейсы: неявный контракт (00:15–00:30)
[`examples/02-interfaces`](examples/02-interfaces/main.go)

Интерфейс — это **набор сигнатур методов** и больше ничего:

```go
type Stringer interface {
	String() string
}
```

Самое непривычное после Java и C#: тип удовлетворяет интерфейсу
**неявно**. Никакого `implements`, никакого объявления связи — достаточно,
чтобы у типа были нужные методы. Интерфейс может быть объявлен позже типа,
в другом пакете, другим человеком — и всё равно сработает:

```go
type Percent int

func (p Percent) String() string { return fmt.Sprintf("%d%%", int(p)) }
```

`Percent` ничего не знает о пакете `fmt`, но уже удовлетворяет
`fmt.Stringer` — и `fmt.Println(Percent(42))` напечатает `42%`,
потому что `fmt` проверяет: «умеешь `String() string`? тогда вызову».

Отсюда — главная идиома проектирования в Go:

> **Принимай интерфейсы, возвращай конкретные типы.**
> Функция, которая принимает интерфейс, работает с чем угодно,
> включая типы, которые ещё не написаны. Функция, которая возвращает
> конкретный тип, не отрезает вызывающему доступ к его методам.

И второе правило: **интерфейсы маленькие**. В стандартной библиотеке типичен
интерфейс из одного-двух методов (`Stringer`, `error`, `io.Reader`).
Интерфейс на десять методов — почти всегда признак, что вы проектируете
иерархию классов, которой в Go нет.

Проверить, что тип удовлетворяет интерфейсу, можно прямо на этапе
компиляции — так делают в тестах этого семинара:

```go
var _ fmt.Stringer = Percent(0) // не скомпилируется, если String() пропадёт
```

## 3. `error` — это интерфейс (00:30–00:45)
[`examples/03-error-interface`](examples/03-error-interface/main.go)

Семинар 2 закончился на sentinel-ошибках. Теперь видно, что было за
занавесом: `error` — обычный интерфейс из одного метода, встроенный в язык:

```go
type error interface {
	Error() string
}
```

`errors.New` возвращает крошечный тип с этим методом. Когда к ошибке нужно
прикрепить **данные**, объявляют свой тип:

```go
type ValidationError struct {
	Field  string
	Reason string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("поле %q: %s", e.Field, e.Reason)
}
```

Получатель по указателю — стандарт для ошибок: создают их как
`&ValidationError{...}`, и сравнение через `errors.As` рассчитано
на указатель.

**`errors.Is` против `errors.As`.** На семинаре 2 был `errors.Is` — он
ответает на вопрос «это ТА ошибка?» (по значению). `errors.As` отвечает
на другой вопрос — «есть ли в цепочке ошибка ТАКОГО ТИПА?» — и отдаёт её,
чтобы прочитать поля:

```go
var ve *ValidationError
if errors.As(err, &ve) {
	fmt.Println(ve.Field, ve.Reason)
}
```

Оба идут по цепочке обёрток `%w`, так что оборачивать ошибки можно
спокойно — контекст не теряется.

## 4. `any`, type assertion, type switch (00:45–01:00)
[`examples/04-type-switch`](examples/04-type-switch/main.go)

`any` (он же `interface{}`) — пустой интерфейс. Ему удовлетворяет любой
тип, потому что в нём ноль методов. Значение `any` хранит пару
**(конкретный тип, значение)**.

**Type assertion** достаёт конкретный тип обратно. Всегда берите форму
с двумя результатами — форма без `ok` паникует при промахе:

```go
s, ok := v.(string) // ok == false, если внутри не строка
n := v.(int)        // panic, если внутри не int — так не пишут
```

Несколько проверок подряд — это **type switch**:

```go
switch x := v.(type) {
case nil:
	return "nil"
case int:
	return fmt.Sprintf("число %d", x)
case string:
	return fmt.Sprintf("строка «%s»", x)
case fmt.Stringer: // в case может стоять и интерфейс
	return x.String()
default:
	return fmt.Sprintf("неизвестный тип %T", x)
}
```

В каждой ветке переменная `x` имеет тип из `case` — это не магия,
а вывод типа по веткам.

> **Когда `any` уместен, а когда нет.** Type switch — инструмент для
> границ системы: разбор JSON без схемы, форматирование произвольных
> значений, отладочная печать. Если вы пишете type switch **внутри**
> своей предметной логики — скорее всего, вам нужен обычный интерфейс
> с методом, и ветки превратятся в полиморфные вызовы. `any` + switch —
> это `instanceof` из Java, и репутация у него та же.

## 5. Ловушка: nil внутри интерфейса (01:00–01:10)
[`examples/05-nil-interface`](examples/05-nil-interface/main.go)

Интерфейс равен `nil`, только когда пусты **обе** части пары
(тип, значение). Это порождает самый знаменитый баг с интерфейсами:

```go
func defaultConfig() fmt.Stringer {
	var c *Config // nil-указатель, но с типом *Config
	return c      // интерфейс = (*Config, nil) — это НЕ nil!
}

c := defaultConfig()
fmt.Println(c == nil) // false — проверка на nil не спасла
```

Функция «вернула пустое значение», а `!= nil` говорит «всё есть».
Дальше вызов метода уходит в nil-получатель и паникует — или не паникует,
если метод написан аккуратно.

Два правила:

1. Функция, возвращающая интерфейс, в случае «пусто» возвращает
   **голый `nil`**, а не типизированный указатель: `return nil`,
   а не `return c`, где `c` — nil-указатель.
2. Метод, которому разрешено работать на nil-получателе, проверяет его
   первой строкой: `if c == nil { return "<no config>" }`. Так устроены,
   например, сгенерированные protobuf-структуры.

## 6. Сортировка: `sort.Interface` (01:10–01:20)
[`examples/06-sorting`](examples/06-sorting/main.go)

Классический способ отсортировать свой тип — реализовать `sort.Interface`
целиком, все три метода:

```go
type Interface interface {
	Len() int
	Less(i, j int) bool
	Swap(i, j int)
}
```

```go
type ByScoreDesc []Student

func (s ByScoreDesc) Len() int           { return len(s) }
func (s ByScoreDesc) Less(i, j int) bool { return s[i].Score > s[j].Score }
func (s ByScoreDesc) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }

sort.Sort(ByScoreDesc(group))
```

Обратите внимание: `sort.Sort` ничего не знает про студентов — он умеет
сортировать **что угодно, у чего есть длина, сравнение и обмен**. Это тот же
приём, что в разделе 2, только интерфейс из трёх методов.

`Less` обязан задавать **строгий порядок**: `Less(i, i)` всегда `false`,
и не бывает `Less(i, j) && Less(j, i)`. Нарушите — и `sort.Sort` отдаст
непредсказуемо перемешанный слайс без единой ошибки.

Современная альтернатива (Go 1.21+) — `slices.SortFunc` с функцией
сравнения, тогда интерфейс не нужен вовсе:

```go
slices.SortFunc(group, func(a, b Student) int { return a.Score - b.Score })
```

Разовая сортировка — `SortFunc`, именованный критерий, который
переиспользуется и читается по имени, — тип с тремя методами. В задаче 3
вы реализуете именно классический интерфейс: это лучшая тренировка
«удовлетворить чужой контракт неявно».

## Вопросы, которые задают почти всегда

**«Чем интерфейс отличается от абстрактного класса?»**
Тем, что его нельзя инстанцировать и у него нет состояния — как и у
абстрактного класса. Но абстрактный класс требует явного наследования
и тащит за собой иерархию, а интерфейс в Go удовлетворяется неявно
и задним числом: автор типа может никогда не слышать об интерфейсе,
которому его тип уже соответствует.

**«А множественное наследование через интерфейсы?»**
Тип может удовлетворять скольким угодно интерфейсам одновременно — это
просто факт о наборе его методов, а не отношение. `bytes.Buffer`,
например, одновременно `io.Reader`, `io.Writer` и `fmt.Stringer`.

**«Интерфейс или дженерик?»**
Интерфейс решается во время выполнения (динамическая диспетчеризация),
дженерик — во время компиляции. Правило: если типы нужно хранить вместе
в одном слайсе или выбирать поведение в рантайме — интерфейс; если код
одинаков для разных типов и важна скорость — дженерик. До дженериков
мы ещё дойдём.

**«Почему методы на своих типах только в своём пакете?»**
Иначе любой мог бы добавить метод к любому типу из любого пакета, и
поведение чужих библиотек менялось бы непредсказуемо. Ограничение защищает
автора типа: полный список его методов виден в его собственном пакете.

## Чего мы сегодня НЕ трогали

Чтобы не было ощущения, что интерфейсы уже пройдены:

- **Встраивание (embedding)** — включение структуры в структуру
  и интерфейса в интерфейс; «наследование для бедных» в Go
- **Дженерики и constraints** — интерфейсы как ограничения типов-параметров
- **`io.Reader` и `io.Copy` глубоко** — мы трогали только `io.Writer`
  в дополнительной задаче
- **Рефлексия** (`reflect`) — что делать, когда type switch не справляется
- **Горутины и каналы** — по-прежнему впереди
